## Step 1.5: rule-overlap simulation

**`is_engine_owned_path` branches.** The order is: empty → False; R1 (segment); R2 (symlink); except → False. I ran every RED fixture through this order:
- `.bytedigger-sessions.json`, `my.bytedigger/x`, `bytedigger/x`: no segment equals `.bytedigger`, so R1 is False. They do not exist and are not symlinks, so R2 is False. Result False, as the test expects.
- `inside_dir/f.py`: R1 False. The parent is a symlink, but it resolves inside root, so R2 is False. Result False.
- `dangling_in` (link → `repo/does-not-exist`): a non-strict `resolve()` lands *inside* root. Only an explicit dangling check produces True. The spec (L58-59) requires that check, and the test pins it. This is consistent and is a useful trap for a lazy implementation.
- `venv/lib.py`: the parent component `venv` escapes root, so R2 is True.
- Provider returns `None` or `""` or raises: degrades to `.bytedigger`. The second module-level `foreign_state_dirname` (config_provider.py:382, which shadows the one at :242) raises `AttributeError` or returns `None`. The `engine_state_dirname` wrapper must catch both, and the spec covers both.

**Simulation gap.** A path with `..` is not normalised by R1. For example, `.bytedigger/../src/a.py` has a `.bytedigger` segment and is reported as owned, although it is user content. This is in the adversarial edges below.

**Lint classification order** (no key → malformed → filters-without-ref; then stale):
- AC7 malformed case: an entry with `bogus` class must yield only the malformed problem, not also a filters problem. The spec ordering allows this.
- `_SRC_FILTERED` passes `[]` as the first positional argument to `drop_engine_owned`. An empty list literal has no verb, so it must not count as a site. The spec allows this; GREEN must guard the index.

## Adversarial edges (not covered by any AC)

1. **`..` in a path.** `.bytedigger/../src/a.py` would be reported owned and dropped from the security scan and the commit. `src/../.bytedigger/x` should be owned. Expected under the spec: undefined. It should be: `posixpath.normpath` before R1, then the first not owned and the second owned.
2. **Absolute path not lexically under `repo_root`.** Example: `git_cwd=/var/…`, path `/private/var/…/x`, or the repo living under a `.bytedigger` ancestor such as bd#93's `~/.bytedigger/runs/<id>/wt`. If R1 then scans every segment of the absolute path, every path is owned. The security-lint set becomes empty and the gate fails open. Expected: R1 False for paths not under root (M3).
3. **Symlinked dir inside an untracked dir.** Example: `pkg/vend -> /outside/realvenv`. With Python <3.13, rglob yields `pkg/vend/lib.py`, a regular file, so the old `f.is_symlink()` check misses it. Expected under the spec: R2 parent-component → dropped. No test covers it (F6).
4. **Engine state already tracked** (committed by the old bug). `git diff --name-only red..HEAD` and `diff HEAD` still list `.bytedigger/events.jsonl`. Expected: dropped by R1 in the scan sets. `git add -A` leaves tracked modifications under `:(exclude)` unstaged, so the tree stays dirty → F2 path.
5. **Multi-segment host dirname** (provider returns `state/bd`). Segment equality never matches, so R1 is a silent no-op, while the pathspecs `:(exclude)state/bd` do work. The predicate and the pathspecs disagree. Expected: reject a non-single-segment dirname and degrade to `.bytedigger` with an event, or match as a path prefix.
6. **Symlink loop** (`a -> b`, `b -> a`). `resolve()` raises `RuntimeError`/`OSError`, so R2 degrades to owned and the path is dropped with an event. This is consistent with §4 but untested.
7. **Fresh-run fix cycle, no `.gitignore`.** The only dirt is `?? .bytedigger/`. `_dirty_worktree_guard` self-heals, but the tail is filtered to `[]`, so the tree is still dirty and the result is `E_FIX_UNCOMMITTED_CHANGES` (F2).
8. **User-authored escaping or dangling symlink in the manifest.** Example: `bin/tool -> /usr/local/bin/tool`. The manifest commit drops it, but the checkpoint `git add -A` commits it (F3).

## Findings

1. **[MAJOR] F1: tree-scan site detection (§2.3) is under-broad, and existing gates already bypass it.** File: spec L96-103.
   - **Varargs git helpers are invisible.** `preflight.py:216` and `:355` call `_git(top, "ls-files", "-z", "--others", "--exclude-standard")`. The first positional argument is `top`, not a list literal. That is a live gate's changed-file set, and it lists untracked engine state.
   - **The verb is taken only from element 0 or 1.** That misses `["git", "-C", root, "status"]`, `["git", "-c", "k=v", "add"]` and `["git", "--no-optional-locks", *args]` (preflight.py:125).
   - **Several APIs are not kinds:**
     - `git_status_porcelain` (git_diff.py:174), unless matched by suffix
     - the port methods `.diff_files(` and `.status_porcelain(`
     - `Path.glob("**…")`, `glob.glob(…, recursive=True)`, `os.scandir`, `os.listdir`, `Path.iterdir`
     - the `diff --name-only` verb (authored_boundary.py:218, precommit_enforce.py:154, phase_5_implement.py:8160)
   - **The scan scope is an allow-list.** `workflows/**`, `lib/**` and top-level files leave out `security/`, the home of the security gate, and `scripts/` (`scripts/lib/citation_verifier.py` has a walk).
   - This repo has already recorded this exact lesson: CONTRACTS_SPEC.md:278-292, "the enumeration is exhausted at the API level… incidental coverage is not coverage."
   - The RED does not pin the kinds the spec does list. AC7 covers only `os.walk` and `git-status`, so a lint that skips `git-ls-files`, `ls_files_others`, `status_porcelain`, the BinOp form or the `"git"`-prefixed form passes everything.

   **Fix:**
   - (a) Make the verb the first element after `"git"` that is not an option, skipping `-C <x>`, `-c <x>` and `--*`.
   - (b) Add a varargs rule: any call whose callee name contains `git` and that has a string-constant positional argument in `{status, ls-files, add}` or `diff` + `--name-only`.
   - (c) Add the kinds `glob`, `iglob`, `scandir`, `listdir`, `iterdir` and `git-diff-names`, and suffix-match `*status_porcelain` / `*diff_files`.
   - (d) Scan the whole package minus `conformance/` and `tests/` (a deny-list).
   - (e) In AC7, add one synthetic source per kind, plus the BinOp, `-C`-prefixed and varargs forms, each expected to be reported as unkeyed.

2. **[MAJOR] F2: dirty-tree gates are not wired, and §2.2-3 turns pollution into a terminal failure.** Files: `phase_6_fix_integrity.py:329,354`, `phase_6_review.py:4265-4289`.
   - In a fresh run with no `.gitignore`, `?? .bytedigger/` makes `_dirty_worktree_guard` self-heal through `_autocommit_fix_tail`.
   - After GREEN, `_filter_gitignored_paths` drops the tail, so `tail_paths == []` and the function returns `{"tail_committed": False}`.
   - The second status read is still dirty, so the result is `E_FIX_UNCOMMITTED_CHANGES` with `recoverable=False` (fix_integrity.py:375-385).
   - Today the same run "succeeds" by committing engine state. After GREEN it hard-fails. This breaks the issue's "do not trip … in a fresh run" and the "degrade, don't fail" principle.
   - Related: `_checkpoint_green_worktree`'s dirty check (phase_5:5078-5086) counts engine state in `n_files` and `swept`, so it can never return `clean`. AC6 will still bless that `git-status` site as `filters`, because the function references `engine_owned_pathspecs` (see M2).

   **Fix:**
   - Add a §2.2-7: parse the porcelain lines in `_dirty_worktree_guard` (both reads), `_autocommit_fix_tail` and the checkpoint step-3 check, then pass them through `drop_engine_owned`. Note that the dir form `.bytedigger/` satisfies R1.
   - Add an AC on a real tmp repo where the only dirt is `.bytedigger/events.jsonl`: `_dirty_worktree_guard(...)` is `None` and the checkpoint returns `outcome == "clean"`.
   - List these producers in the §1 table.

3. **[MAJOR] F3: R2 is applied to the commit manifest, which is over-broad and inconsistent with the checkpoint.** Files: spec L56-60, L84-86.
   - `_filter_gitignored_paths` will drop any user- or agent-authored symlink that escapes root or dangles from every manifest commit (phase_5 :2531, :8256, :8270; phase_6 :4287, :4596, :4626). Examples are `bin/tool -> /usr/local/bin/tool` and a relative link to a file created later.
   - Meanwhile `_checkpoint_green_worktree`'s R1-only pathspecs commit the same link.
   - The dropped link leaves the tree dirty, which leads into F2.
   - The incident behind R2 is a *lint* reading through the venv link, not a commit.

   **Fix:**
   - Apply R2 only to sets whose files have their content read: the security-lint and GREEN-lint sets and the walkers. The commit manifest should use R1 only, for example `drop_engine_owned(..., *, symlinks: bool = True)` with `_filter_gitignored_paths` passing `symlinks=False`.
   - Add an AC: `_filter_gitignored_paths(["link_out"], repo) == ["link_out"]` for a link that escapes root.
