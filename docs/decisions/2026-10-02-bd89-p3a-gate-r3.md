## Findings

### MAJOR (block GREEN)

1. **F1: the op2c retry at cycle 3 is refused by the engine. The spec's "also at cycle 3" claim is false, and the RED cannot see it.**
   - The engine retries only when `cycle_count < _MAX_VALIDATION_CYCLES` (`= 2`, `engine.py:469`) or when `gate_budget_ok and cycle_count < _GATE_BUDGET_HARD_BACKSTOP` (`= 6`, `:474`); the check is at `engine.py:699-705`.
   - At cycle 3, op2c returns `cycle_count = 2` and no `gate_budget_ok`, so the result falls through to the terminal exit.
   - `gate_budget_ok` is a control key (`engine.py:199`). It is never forwarded across retries, so op2c must set it itself.
   - The repo already has the exact precedent for a same-cycle re-entry at a resolved cycle 3: GH1018 P3, `phase_5_implement.py:3184-3193`, which sets `"cycle_count": max(cycle - 1, 0), "gate_budget_ok": True`. That route is still bounded by `_GATE_BUDGET_HARD_BACKSTOP` and `_MAX_SAME_CYCLE_RETRIES = 3`.
   - The `_surgical_fallback` precedent the spec copies has the same latent cycle-3 defect, so copying it is not sufficient.
   - **Fix (spec r4 plus RED amendment):**
     - op2c adds `gate_budget_ok: True` to the retry data, citing GH1018 P3. The spec text replaces "so the engine's next_cycle = cycle_count + 1 re-runs the SAME cycle, also at cycle 3" with the actual engine condition.
     - The AC16 matrix asserts `data["gate_budget_ok"] is True`.
     - The engine-hop test is parametrised over `cycle` in {2, 3} (seed `_rework_cycle_high = cycle - 1` or similar). At cycle 3 it asserts exactly one `phase_retry_triggered` with `cycle == 3` and a fresh spy call with `extra_data["cycle"] == 3`.
     - Both new assertions are red today for the right reason (op2c absent), and they turn green only with the flag.
