## Step 1 — spec-internal consistency (literal-token drift)

Tokens checked across §2/§3/§4: `receipt_rung`, `preflight_receipt` (event), `preflight_rung` (cfg key), `extra_data["preflight"]`, `ladder_table`, `record_validation_reject(..., preflight=)`, `gate: "validation"`. The names are consistent. The drift is in the **shapes**:

- **The `preflight` record has two shapes.** op2 (spec:32) writes `extra_data["preflight"] = {"status": ...}`. op3 (spec:39) reads `prev.data.get("preflight")` as "the op2 record" and says the row gains `{"status", "red_step"}`. ladder_table (spec:40) groups by `red_step`. The op2 record never carries `red_step`, and the RED pins that shape: test:247 asserts `== {"status": state}` and test:298 asserts `== {"status": "fresh"}`. So production rows can never have a non-null `red_step`. AC9b (test:421) and AC9c (test:455) use a hand-built `{"status": "red", "red_step": "cite"}` that the producer cannot emit. → MAJOR-2.
- **op1 contradicts itself.** spec:24-25 says `receipt_rung` "calls `verify_receipt` and nothing else". But `red_step` ("first red step name from the receipt") requires reading `receipt.json` `steps[]` (preflight.py:40). → MINOR-1.
- **"AC9" is used twice.** It labels the sibling-pass AC (spec:62) and is also the prefix of AC9a/9b/9c (spec:59-61). → MINOR-2.

**Concern 5 (receipt phase `"red"` at pre-GREEN; is a receipt ever produced there?)**

The phase is semantically right: the RED tests exist and must fail. But no producer can put a fresh receipt there in an engine-driven run:

- No engine code calls `run_preflight` (only `run.py:253` CLI dispatch).
- The phase-5 loop runs `invoke_red_llm → write_red_artifact → commit_red_tests` (phase_5_implement.py:8373-8375) immediately before validation. Any host preflight run before the engine started predates the RED tests, and HEAD moves at `commit_red_tests`. `verify_receipt` then returns `stale` (head mismatch, preflight.py:264) or `missing` (no receipt, or a green-phase one, preflight.py:257).
- So `fresh`/`red` are effectively unreachable in production. AC3's four states are reachable only through test pre-staging.

The §2 reading rule (spec:41) makes this harmful, not merely empty: "A REJECT with `red`/`stale`/`missing` = a script would have, or could have, caught it first." If every row is `stale`/`missing`, the `ladder_table` will attribute 100% of gate rejects to "script could have caught it". That is exactly the evidence spec:21/§7 says the gate-replacement PR will cite. The bias points toward removing a hard gate (`never_skip_opus_validation_gate`). → MAJOR-5.

## Adversarial edges (not covered by any §3 AC)

- **E1 regression shield / add-only (concern 1):** in default mode with a `fresh` vs `red` receipt, every `invoke_llm_subprocess` kwarg except `extra_data["preflight"]` must be identical, and identical to `{"mode":"off"}`. No AC pins this (MAJOR-3).
- **E2 end-to-end threading:** drive `_invoke_validation_llm → _write_validation_doc → _verify_validation_citations → _gate_on_validation` with a FAIL verdict at cap and assert that `detail.preflight` is non-null in the row (MAJOR-1).
- **E3 legacy rows:** `ladder_table` over rows whose `detail` has **no** `preflight` key, which is every historical row. Is that `none` or skipped as malformed? Also undefined: `detail.preflight` that is a non-dict (`"fresh"`), and a dict without `status`. (§1x)
- **E4 ambient cwd:** with no `git_cwd`/`current_worktree_path`, `_resolve_git_cwd` falls back to scratchpad-climb/`Path.cwd()` (phase_5_implement.py:2057-2064). The rung then hashes and reads the receipt of whatever repo the process sits in: HAL, or the engine's own checkout. The spec uses `_resolve_git_cwd`, not the ambient-aware `_resolve_git_cwd_with_source` (:2067-2072, GH1220). The event should carry, or be suppressed on, an ambient source; otherwise foreign receipts pollute the evidence. It also adds a whole-repo `git diff --binary` to every validation call in sibling tests.
- **E5 empty / explicit-null config:** `preflight_rung: {}` and `preflight_rung: None` (Step 1.5 table).
- **E6 stale-but-was-red:** a receipt with `ok:false` that has gone stale. Should `red_step` be the receipt's red step or `None`? The spec's "first red step name from the receipt" says the former. AC2 only covers stale-from-green.
- **E7 row size cap:** `emit_reject_reason` drops any row over 4096 bytes whole (reject_log.py:132-133). The added `preflight` object can push near-cap rows over, so the reject itself goes unrecorded. Small, but it is a behaviour change in a "no other field changes" op.
- **E8 ladder_table tie order:** equal `rejects` counts have no defined secondary sort. AC9c avoids ties (5/4/3/2/1), so output is non-deterministic across Python dict orders only when input order differs. Name a tie-break (status, red_step).
- **E9 resume:** `invoke_validation_llm` is `resume_sentinel=True` (phase_5_implement.py:8380). On resume the cached result is replayed: no new `preflight_receipt` event, and `extra_data["preflight"]` comes from an older tree. Either accept this or state it.

## Findings

1. **MAJOR-1** — `preflight` is dropped between the gate call and the reject logger. `_write_validation_doc` rebuilds `data` without it (phase_5_implement.py:7206-7223; step order :8380-8383). op3 therefore logs `null` on every real run. AC9b passes only through a hand-built `prev` (test:400-430). **Fix:** add an op threading `preflight` through `_write_validation_doc` (and confirm `_verify_validation_doc_impl` forwards it), plus an end-to-end AC (E2).
2. **MAJOR-2** — The record shape differs between op2 and op3. op2 emits `{"status"}` (spec:32; RED test:247, :298); op3/ladder_table need `{"status","red_step"}` (spec:39-40). `red_step` can never be non-null in production. **Fix:** op2 forwards `{"status","red_step"}` from `receipt_rung`, and test:247/:298 are updated to match.
3. **MAJOR-3** — The add-only invariant (spec:20) has no AC beyond call count. A GREEN that conditions the prompt or kwargs on the rung passes every RED. **Fix:** AC asserting default-mode kwargs minus `extra_data["preflight"]` == off-mode kwargs, for both a `fresh` and a `red` receipt (E1).
4. **MAJOR-4** — AC9 ("test_bd141_check_ladder.py passes unchanged", spec:62) contradicts default-on op2. L16 asserts the exact `extra_data` key set (test_bd141_check_ladder.py:544-545) and will fail for all 7 params. **Fix:** decide default-off, or amend L16 explicitly and restate AC9.
5. **MAJOR-5** — No production producer exists for a `fresh`/`red` phase-`red` receipt at the pre-GREEN point. The engine never runs `run_preflight`, and `commit_red_tests` (phase_5_implement.py:8375) moves HEAD after any host run, so `verify_receipt` returns stale/missing (preflight.py:257, :264). The §2 reading rule (spec:41) then counts every reject as "script could have caught it", which biases the evidence for removing the hard gate. **Fix:** name the producer (who writes a red receipt after `commit_red_tests` and before `invoke_validation_llm`), or reword spec:41 so `stale`/`missing` mean "no evidence" and are excluded from the replacement argument. Add an AC or measurement showing a non-trivial `fresh` share before the table is cited.
6. **MINOR-1** — op1 says "calls `verify_receipt` and nothing else", but `red_step` needs a receipt read (spec:24-25 vs preflight.py:40).
7. **MINOR-2** — The AC9 label collides with AC9a/b/c (spec:59-62).
8. **MINOR-3** — Mode-dispatch ambiguity for `{}` and explicit `None`. `{"mode":"verify"}` is never driven by the RED (Step 1.5).
9. **MINOR-4** — AC5 claims full-kwargs equality, but test:292 checks only the `extra_data` key set.
10. **MINOR-5** — Spec is silent on `extra_data["preflight"]` content for `error` and `config-error`, and on the ambient-cwd fallback (E4), legacy rows (E3), tie order (E8) and the 4096-byte row cap (E7).

VERDICT: REJECTED
