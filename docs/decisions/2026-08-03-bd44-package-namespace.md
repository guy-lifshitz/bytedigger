# BD44 — переезд в `bytedigger_engine/`

## §0. Премисса — проверена СБОРКОЙ, а не чтением

Собрано из чистого клона `385b1ed`: `python3 -m pip wheel . --no-deps` в `engine_py/`.
Содержимое колеса `bytedigger_engine-0.1.2-py3-none-any.whl`, верхний уровень:

```
всего верхнеуровневых записей: 56
  плоских модулей .py:        51
  каталогов-пакетов:           5   (lib, scripts, security, workflows, conformance)
пакета bytedigger_engine:     НЕТ
```

Занятые generic-имена (замерены, не перечислены по памяти): `config_provider.py`,
`contracts.py`, `ctx_floor.py`, `doctor.py`, `engine.py`, `event_log.py`, `io_utils.py`,
`run.py` — и, что хуже, четыре каталога с именами `lib`, `scripts`, `security`,
`workflows`. Каталог `lib` в site-packages — это уже не риск коллизии, а почти
гарантия.

Три числа сведены (rev6): **56** — записи в КОЛЕСЕ; **57** — замер issue в
site-packages; **58** — мой замер там же. Разница между колесом и site-packages —
служебные каталоги установки (`dist-info`, `__pycache__`), между 57 и 58 — состав
venv на разных машинах. Предмет ни от одного из трёх не зависит: пространства имён у
пакета нет ни при каком счёте. Базой AC3 служит НЕ число, а утверждение «ровно одна
запись» — именно потому, что счёт нестабилен.

**Третий пункт issue подтверждается конструктивно:** `[project.scripts]` объявляет
`bytedigger-engine = "run:main"`, то есть точка входа висит на верхнеуровневом `run`.
Ни `bytedigger`, ни `bytedigger_engine` в колесе не существует, поэтому у
установившего пакет нет ни одного угадываемого имени для импорта.

## §1. §1b — цена переезда замерена ДО заморозки

Наивный `git mv` сломает всё: модули импортируют друг друга по верхнеуровневым именам.

```
файлов с внутренними абсолютными импортами: 172
всего таких импортов:                       758
пример: run.py — 20, llm_subprocess.py — 14
```

Это и есть настоящий объём работы, и его надо назвать числом до заморозки, а не
обнаружить в GREEN. Механическая часть — переписывание 758 импортов; риск —
динамические импорты (`importlib`, `__import__`, строковые имена в конфигах), которые
AST-обход НЕ видит и которые обязаны быть отдельно перечислены в §2.3.

## §2. Контракт

### §2.1 Форма (задана постановщиком, не изобретается здесь)

- Один пакет `bytedigger_engine/`; всё, что сегодня плоско, уезжает под него.
- Console-script `bytedigger-engine` СОХРАНЯЕТСЯ (пользовательский интерфейс не ломаем),
  меняется только его цель: `bytedigger_engine.run:main`.
- `import bytedigger_engine` — публичная точка входа, обязана существовать.
- Ломающее изменение импортов ⇒ версия **0.2.0**.

### §2.2 Что считается сделанным

Приёмка — **реальной установкой**, не зелёным CI:

1. собрать колесо из репозитория;
2. `python3 -m venv` — ЧИСТЫЙ venv, без наследования site-packages;
3. `pip install <колесо>` — exit 0;
4. `python -c "import bytedigger_engine"` — exit 0;
5. `bytedigger-engine --list` — exit 0 и **21 workflow**;
6. в site-packages venv'а **нет** ни одного из замеренных generic-имён верхнего уровня
   (ни `contracts.py`, ни каталогов `lib`/`scripts`/`security`/`workflows`/`conformance` —
   пять каталогов, а не четыре).

Пункт 6 — предмет лота; пункты 4-5 — то, что нельзя сломать по дороге.

### §2.3 Края, которые обязаны быть перечислены (§1n)

- **Динамические импорты.** AST-обход считает только статические; строковые имена
  модулей (`importlib.import_module("contracts")`, конфиги, `--module` флаги) обязаны
  быть найдены отдельным грепом и перечислены поимённо в GREEN. Пропущенный
  динамический импорт — это отказ в рантайме у пользователя, а не красный тест.
- **package-data.** `[tool.setuptools.package-data]` адресует `lib.plugins.*`,
  `security`, `scripts.red_lint` — все пути обязаны переехать вместе с пакетами,
  иначе колесо соберётся, а YAML/MD не доедут.
- **Тесты репозитория** импортируют те же верхнеуровневые имена; они переезжают
  вместе, но их правка НЕ должна маскировать сломанный прод-импорт.
- **`conftest.py`** в корне репозитория — проверено, он **0 байт** и в разрешении путей
  не участвует. Значение имеет `engine_py/tests/conftest.py:37-49` — см. §5.

## §1c. Замеры второго круга (сделаны после первой редакции)

1. **21 workflow ПЕРЕЗАМЕРЕН, не взят из issue.** Установка текущего колеса в чистый
   venv (`python3.14`), затем `bytedigger-engine --list` → JSON-массив, `len == 21`,
   rc=0. Число годится как численный AC: живая база есть.
   В том же venv верхнеуровневых записей site-packages (без pip/setuptools/dist-info):
   **58** — сходится с 57 из issue с точностью до служебных каталогов.
2. **Динамические импорты найдены, и один из них — настоящая ловушка.**
   `doctor.py:90` держит имена модулей СТРОКАМИ:
   `["stub_passability", "red_lint_checks", "verdict_gate", "spec_cite", "tier_gate"]`,
   далее `__import__(mod_name)`. AST-обход §1 их НЕ видит. После переезда они обязаны
   стать `bytedigger_engine.*`, иначе `doctor` отрапортует «missing module» — отказ у
   пользователя в диагностическом инструменте, а не красный тест.
   `forbidden_import.py` содержит те же токены как ДАННЫЕ (паттерны линта), а не как
   вызовы — трогать не надо; в области правки различать эти два случая обязательно.
3. **Хорошая новость, снимающая риск: регистрация workflow ЯВНАЯ.**
   `workflows/__init__.py` вызывает `engine.register("echo", …)` поимённо; открытия по
   именам файлов нет. Значит переезд не может тихо изменить состав `--list` — он может
   только сломать импорт целиком, что видно сразу.
4. **Точка входа расширяет пространство имён В РАНТАЙМЕ — и она не одна.**
   rev1 называла две вставки в `run.py:24-27`. Это занижение в тридцать раз.
   Перезамерено AST-обходом (исключая `tests/` и мусор сборки `build/`):

   ```
   ВЫЗОВОВ sys.path.insert/append в коде: 63  в 42 файлах
   в т.ч. lib/cost_rollup.py, lib/dispatcher_report.py, doctor.py, event_log.py,
          workflows/*, error_codes.py, classify_incident.py …
   ```

   Переезд обязан удалить ВСЕ 63, иначе пакет продолжит работать через path-хак и
   класс коллизий переживёт починку (AC7).

5. **Ловушка данных, в которую rev1 попала сама.** Те же символы встречаются как
   СТРОКОВЫЕ ЛИТЕРАЛЫ — 7 вхождений в трёх файлах: `silent_success.py`,
   `suite_safety.py`, `workflows/phase_5_implement.py` (последний — текст промпта
   продукта). Проверка подстрокой по установленным файлам ТРЕБОВАЛА БЫ править текст
   продукта, то есть нереализуема. Поэтому AC7 считает ВЫЗОВЫ по AST, а не подстроки —
   ровно то различие, о котором предупреждает §1c.2 и которое rev1 не применила к себе.

6. **Версия объявляется в нескольких местах** (в `version_parity.DECLARATIONS` их шесть; я насчитал четыре файла, потому что два объявления живут в одном pointer-файле), и за паритетом следит
   `scripts/version_parity.py`: `engine_py/pyproject.toml`, `package.json`,
   `packaging/pypi-pointer/pyproject.toml` (собственная версия И пин
   `bytedigger-engine==…`). Поднять только первую — значит оставить
   `pip install bytedigger` раздающим 0.1.2 (рецидив задокументированного инцидента
   0.1.0→0.1.1). Покрыто AC6.

7. **Публичная поверхность помимо CLI:** `examples/library/*.py` показывают
   `from contracts import …` как документированный способ употребления библиотеки.
   Переезд ломает их молча — они входят в область (AC10).

## §3. Acceptance criteria

Все AC читают АРТЕФАКТ, который получит пользователь: колесо, собранное из
репозитория, и чистый venv, куда оно установлено. Ни один AC не читает исходное
дерево — кроме AC10, где предмет и есть исходник примеров.

- **AC1 (§1l).** `import bytedigger_engine` в чистом venv — exit 0. Сегодня
  `ModuleNotFoundError`.
- **AC2 (щит, интерфейс не ломаем).** `bytedigger-engine --list` — exit 0 и ровно
  **21** workflow. Число — живая база, замеренная на ДО-переездном колесе.
  Разбирается ТОЛЬКО JSON, изолированно от посторонних строк вывода.
- **AC3 (предмет, rev2 — переписан).** Дистрибутив владеет **РОВНО ОДНОЙ**
  верхнеуровневой записью в site-packages, и это `bytedigger_engine`. Источник —
  `RECORD`/`top_level.txt` самого колеса, а не список имён. rev1 проверяла белый
  список из 13 замеренных имён: реализация, оставившая 43 других generic-имени,
  проходила бы её насквозь. «Ни одного из перечисленных» ≠ «не занимает верхний
  уровень».
- **AC3b.** Пакет НЕ пуст и НЕ namespace-заглушка: содержит `__init__.py` и не менее
  сорока модулей — иначе пустой каталог удовлетворял бы AC3.
- **AC4 (непустой корпус).** Печатается число верхнеуровневых записей дистрибутива и
  число модулей внутри пакета; оба ассертятся как > 0. Величины берутся из артефакта,
  а не из констант теста (rev1 сравнивала две свои же константы — тавтология).
- **AC6 (версия, rev2 — расширен).** Колесо объявляет **0.2.x**, И
  `scripts/version_parity.py` проходит, И pointer-пакет пинит
  `bytedigger-engine==0.2.x`. Без последних двух `pip install bytedigger` продолжит
  раздавать 0.1.2.
- **AC7 (path-хак снят, rev2 — по AST).** В установленном пакете **ноль ВЫЗОВОВ**
  `sys.path.insert/append`. Считается разбором AST, а не подстрокой: те же символы
  живут строковыми литералами в тексте промпта продукта (§1c.5), и подстрочная
  проверка потребовала бы править продукт ради теста.
- **AC7b (поведенчески, rev2 — правильная сторона).** После `import bytedigger_engine`
  бареный `import contracts` и `import config_provider` обязаны падать
  `ModuleNotFoundError`. rev1 зондировала `phase_2_explore` — модуль из `workflows/`,
  то есть проверяла не тот класс: реализация, спрятавшая только `workflows/`, но
  оставившая плоские generic-имена, проходила её.
- **AC8 (строковые имена).** `doctor.check_gates_importable` и `check_engine_imports`
  в чистом venv не рапортуют «missing module».
- **AC9 (package-data, rev2 — новый).** Ассеты, объявленные в
  `[tool.setuptools.package-data]` (semgrep-правила, red-lint ruleset, plugin YAML/MD),
  присутствуют в колесе ПОД пакетом. Иначе колесо соберётся зелёным, а правила не
  доедут до пользователя.
- **AC11 (rev3 — РЕШАЮЩИЙ).** Ни один модуль ВНУТРИ пакета не импортирует соседа
  голым верхнеуровневым именем. Набор соседей выводится ИЗ АРТЕФАКТА. Без этого AC
  вся остальная таблица описывает лишь ФОРМУ дерева, и `package_dir`-ремап с
  иначе написанным path-хаком проходит её при НУЛЕ переписанных импортов из 758 —
  то есть переезда не происходит вовсе.
- **AC11b (rev3).** После прогона ТОЧКИ ВХОДА (`run.main`), а не только импорта
  пакета, `sys.path` не вырос и плоские имена не резолвятся. Хаки живут на пути
  консольного скрипта, поэтому момент замера решает.
- **AC10 (публичные примеры, rev3 — набор имён ВЫВОДИТСЯ, корпус расширен).** `examples/library/*.py` импортируют
  через `bytedigger_engine`, а не через верхнеуровневые имена. Это документированный
  способ употребления библиотеки; молча сломать его — то же, что сломать CLI.

### §3a. Терминальная ветка точки входа (rev6, MINOR-26)

Точка входа МОЖЕТ завершаться через `os._exit` (`hard_exit`, токен
`HAL_RUNPY_HARD_EXIT`). Это не дефект и не край — это объявленное поведение продукта,
и любой AC, измеряющий прогон точки входа, обязан ПЕРЕЖИВАТЬ его. Практический
вывод, оплаченный четырьмя вакуумами подряд: пост-фактум снимки состояния
непригодны, годится только поточный канал, сбрасываемый построчно, и отсутствие
улики обязано трактоваться как ПРОВАЛ измерения, а не как чистый результат.

Опоры ACов названы явно, чтобы §3 не расходилась с RED:
- AC9 опирается на ЗАМЕР исходного дерева (`lib/plugins/anti_hallucination`: 3,
  `security`: 5, `scripts/red_lint`: 1 — всего 9 ассетов), а НЕ на блок
  `[tool.setuptools.package-data]`, который GREEN переписывает сам.
- AC11b опирается на аудит-хук `sys.addaudithook`, а не на `run.main(...)`:
  `main()` объявлен без параметров.

**Мутация** (не AC, отдельный разрушающий прогон после GREEN): вернуть один модуль на
верхний уровень ⇒ AC3 обязан покраснеть; вернуть один `sys.path.insert` ⇒ AC7.
rev1 объявляла это как AC5 и не реализовала — объявленная и не принуждённая проверка
хуже отсутствующей.
