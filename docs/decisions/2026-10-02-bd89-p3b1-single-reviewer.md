# bd#89 P3b1: remove the parallel 6-role review mode from phase 6 (single reviewer only)

**Status: FROZEN r1** · **Tier:** 3 (engine prod `.py`, Option D) · **Class:** PROCESS (scope-of-build decision, completes the bd#139 default flip) ·
**Chokepoint:** the review plan resolver `_review_plan` (`engine_py/bytedigger_engine/workflows/phase_6_review.py:495`), the single place that turns `org_config` + complexity into a dispatch table and a reviewer count. Its two callers are `_build_review_prompt` (`:763`, prompt producer) and `_aggregate_review_findings` (`:1624`, floor and banner), plus `_invoke_review_llm` (`:1069`, straggler arming and stale-file guard). Removing the `parallel` value at the resolver removes the mode everywhere at once.
**Side of the seam (decision 2026-07-26 §7.1):** engine plus README, two docs rows and CHANGELOG. No orchestrator-flow md, no gate script, no TS.
**Stacked on:** P3a. **Source:** bd#89 checklist row 2 ("6-role review: replace with a single reviewer"), split into P3b1 (this), P3b1b, P3b1c and P3b2 (decorrelated verifier; §4). Template: P3a spec and gates r1..r4. Precedent: `2026-10-01-bd139-phase6-single-reviewer.md` (made single the default, kept `parallel` as an opt-in).

## §1 Problem (measured on the current tree)

- bd#139 made `single` the default but kept `review_fanout: "parallel"` as an opt-in: `_resolve_review_fanout` (`phase_6_review.py:465`), the multi-row branch of `_select_reviewers` (`:482-492`, six `_ROW_*` constants at `:253-258`), the parallel prompt branch in `_build_review_prompt` (`:802-815`, using `PARALLEL_DISPATCH_FRAMING_TEMPLATE` imported at `:166`, defined `canonical.py:37-53`), the `ValueError` to `E_REVIEW_FANOUT_INVALID` mapping (`:778-788`), and the parallel floor in the aggregator (`:1665-1707`, `E_INSUFFICIENT_FANOUT`).
- Row 2 says replace. The parallel mode is the dead half: nothing sets it by default, and it carries the most expensive prompt and three error paths. The straggler arming (`:1096-1143`) only fires for `_reviewer_count >= 2`, so it is dead the moment parallel goes. Verified: `phase_6_review.py:1132` is the ONLY place in `engine_py/bytedigger_engine` that builds a non-None `straggler_cfg` (the other hits are the `straggler_cfg: object = None` parameters of the backends in `lib/reference_backends/*` and `llm_subprocess.py:864,1655,1800`, which only receive it). No other caller arms it.
- Error codes (grep over `engine_py/bytedigger_engine`, excluding tests): `E_REVIEW_FANOUT_INVALID` raised only at `phase_6_review.py:786`; `E_INSUFFICIENT_FANOUT` only at `:1702`; `E_NO_ROLE_FILES` at `:1661` (still raised, kept; §4). Declared at `error_codes.py:98,99,139`; documented in both `engine_py/ERROR_CODES.md` and `engine_py/bytedigger_engine/ERROR_CODES.md` (byte-identical today: `cmp` clean).
- **Resume facts (cited, they drive AC8):**
  - Only steps with `resume_sentinel=True` are cached, via `maybe_read_sentinel` (`lib/step_sentinel.py:139`). In phase 6 those are `invoke_review_llm` (`phase_6_review.py:5967`), `invoke_fix_llm` (`:5985`), `invoke_decorr_llm` (`:5997`). `aggregate_review_findings` is NOT one of them: **no cached aggregate exists** to replay.
  - The sentinel key includes `compute_ctx_hash` (`step_sentinel.py:65`), which folds in `ctx_cfg_sha8({"org_config": cfg, ...})` (`:104`). A pre-upgrade run's `org_config` still carries `review_fanout`, and P3b1 does not edit that dict, so the hash matches and a pre-upgrade `invoke_review_llm` output IS replayed. On replay the stale-file guard (`phase_6_review.py:1145-1152`) does not run, so the per-role files of a pre-upgrade parallel review stay on disk and are what the aggregator then reads. That output is a real finished review, not stale; it must aggregate, not crash.
  - Phase-level: the native phase sentinel is success-only (`lib/phase_sentinel.py`), and bd85 `task_resume` (`lib/task_resume.py`) re-enters a failed phase from step 1 under the same run id, which rebuilds the prompt with the new code. The engine retry uses `retry_from_step` indices (`engine.py:688-706`), which this change does not touch (phase 6 stays 21 steps).

### Degrade, not fail (constraint 1), exact behaviour

- **Old or invalid config** (`review_fanout` = `"parallel"`, `"bogus"`, a number): the single prompt is built, one `review_fanout_ignored` event, no error (AC2, AC3). Before: `"bogus"` returned `E_REVIEW_FANOUT_INVALID` (non-recoverable) and `"parallel"` ran the 6-role mode.
- **Reviewer outage or timeout:** unchanged. `invoke_review_llm` returns its existing error; it is NOT `skip_on_error`, so the existing retry (`retry_from_step`) and, at the cap, `_on_phase_6_abort` (`:5920`, NOT_ASSESSED stub) apply; bd85 resumes it later. Pinned by AC9a (GUARD).
- **Reviewer produced no composite file / empty report:** `aggregate_review_findings` returns `E_NO_ROLE_FILES` with `skip_on_error=True` (`:5969-5975`), so `write_review_artifact` takes the stdout fallback (`:2217`, event `stdout_fallback_used` at `:2282`), and `_derive_fallback_verdict` (`:521`) gives SUSPECT, never PASS. An empty report is SUSPECT through `_zero_findings_roles`. Pinned by AC9b/AC9c (GUARD). No new retry, error code or paid call is added.

Provider principles. No new LLM call and no provider branch. The one prompt is built before any backend is chosen; subscription CLI and API-token modes get byte-identical prompts (AC5). All new tests run with no `ANTHROPIC_API_KEY` and no `claude` on PATH. Deterministic-first: the aggregator, quote-verify, canary and verdict are untouched code; this change only removes a branch.
