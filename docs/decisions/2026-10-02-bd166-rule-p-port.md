## §2 Design

### §2.1 New module `engine_py/bytedigger_engine/one_sided_predicate.py`

Port of HAL `one_sided_predicate.py`. stdlib only, `from __future__ import annotations`,
Python 3.9, no Cyrillic, no env reads, no subprocess, no import from any other
`bytedigger_engine` module. Listed in `core_manifest.json` `core_modules`.

Copied **verbatim** (frozen by HAL GH1373 §2.0): `_FORM_NOT_TO_BE_INT`, `_FORM_NOT_TO_BE_NULL`,
`_POSCTL`, `_BLOCK_START`, `_PRED_ESCAPE = "one-sided-ok:"`, `_CANDIDATE_FORMS`, `_blocks`,
`_scope_for_line`, `_has_escape` (4-line window), `_scope_has_control`, `_iter_candidates`,
`scan_one_sided_predicates`, `summarize_predicates`, `_PREDICATE_IDENTITIES`,
`check_predicate_identities`, the `CANDIDATE_*` constants. Finding dict keys:
`line, subject, form, reason`.

**Declared divergence D1 — the codey test.** HAL's `_CODEY` regex anchors on `[^a-z0-9_]`, so
`exit_code` / `statusCode` are not codey (measured and documented in bd's
`empty_input_assert._tokens`). The port replaces `_CODEY.search(x)` at its two call sites
(`_iter_candidates`, `_scope_has_control`) with the token-based helper that bd already uses:

```python
TS_TEST_SUFFIXES = (".test.ts", ".test.js", ".spec.ts", ".spec.js")
_CODEY_WORDS = frozenset("code rc exit exitcode returncode status".split())
_TOKEN_SPLIT = re.compile(r"[^A-Za-z0-9]+|(?<=[a-z0-9])(?=[A-Z])")
def identifier_tokens(subject: str) -> frozenset[str]: ...   # moved verbatim from empty_input_assert._tokens
def is_codey(subject: str) -> bool: return bool(identifier_tokens(subject) & _CODEY_WORDS)
```

This is NOT a strict superset of HAL's regex (gate r1 m1). It widens in both directions:
- extra candidates/controls on snake_case and camelCase humps: `r.exit_code`, `r.statusCode`
  (intended — the bd-measured HAL defect);
- extra candidates on unrelated humps: `expect(zipCode).not.toBeNull()` becomes a candidate
  (false positive; the `one-sided-ok:` escape covers it);
- extra controls on unrelated humps: `expect(user.zipCode).toBe(90210)` in the same block silences
  a real one-sided predicate (false negative);
- a hump inside a codey word cuts it (`exitcODE` → `exitc`, `ode`) — no realistic subject.
Chosen because it is the helper bd already ships for Rule E, and AC1 demands ONE helper, not two.
All HAL GH1373 Rule P fixtures (`r.code` / `r.stdout`) give identical results. Test B5 pins the
zipCode false positive and false negative as the chosen behaviour, so a later change is a visible
decision. `_CODEY` is not kept (one rule, one site).

### §2.6 Design constraints (issue block)

- **Deterministic first:** the check is regex code; no LLM, classifier or check_ladder step.
- **Provider-agnostic:** the module imports nothing provider-related; the phase-5 helper makes no
  `invoke_llm_subprocess` call. Degradation paths: kill switch → `gate_disabled`; unreadable target
  → recoverable finding; out-of-corpus path → warning event. No crash path.
- **Both backends — by construction:** the result is a pure function of file bytes; nothing on the
  lint path reads `HAL_RUNNER_BACKEND` or reaches a provider. The evidence is structural: B4 (module
  imports nothing from the package, no env, no subprocess) and B7 (the AST of
  `_one_sided_predicate_hits` calls none of `invoke_llm_subprocess`, `check_ladder.*`, `bounded_run`,
  `subprocess.*`, `llm_subprocess.*`). T-B (identical output under `HAL_RUNNER_BACKEND=claude-subprocess`
  and `=anthropic-api`) and T-C (raising `invoke_llm_subprocess`) are regression pins, not proof.
