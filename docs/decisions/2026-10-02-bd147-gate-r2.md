## Findings

**N1 MAJOR: the r2 boundary classifies the findings sidecar two ways, and the facts-pack cache by writer.**
- Spec §1.2 S10 (:34) calls the sidecar "whole file bodies", and §2.1 class M (:71-72) and AUTHORSHIP_SPEC :491 say text "written to a
  file and read back" is "a class-I file body". AUTHORSHIP :476-477 lists "the findings sidecar" as class I, not yet declared.
- The code does something else. `load_findings_thread` runs `json.loads` and takes `data["structured_findings"]`
  (`findings_sidecar.py:37-38`). The prompt renders those fields through `_render_findings(findings)` (`surgical_revise.py:57`, `:82-83`).
  No file body or slice of the JSON reaches the prompt, so by the structural class-E rule (spec :60-64, AUTHORSHIP :480-485) this is
  extraction and re-rendering.
- The facts-pack cache has the same shape (JSON parsed, fields rendered, `facts_pack.py:356-368`). The spec makes it class E because
  the engine wrote it (:62-63, AUTHORSHIP :483). That is a writer test, which §2.1 :48-49 rules out.
- Result: one named member gets class I from one normative sentence and class E from another. A model-output record parsed from disk
  has no stated class. §1.3 promises the inventory "can classify every hit without a new decision", and this hit cannot be classified
  that way. This is the same defect type as r1 F2.
- **Fix (text only, RED unaffected):** state once that a structured record parsed from a file and re-rendered field by field is not a
  file body. Its class follows the origin of the field values: engine-computed values are E (facts cache), model output is M. Then move
  the sidecar out of S10 and the class-I list into class M. It is the GH636 recovery copy of the in-memory S7 thread, so it shares
  S7's limit and re-open criterion. Narrow the class-M sentence (:71-72, AUTHORSHIP :491) to "written to a file and inlined as a body
  or slice".
