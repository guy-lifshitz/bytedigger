## Adversarial edges (not covered by §3)

- **E1 tier rebind + hook (worker).** §2.2 says the hook receives the post-rebind model, but every test runs with
  `tier_rebind=False` and no tier. A GREEN that resolves the hook before rebinding (in `invoke_llm_subprocess`)
  would pass every test.
- **E2 refusal-emits-no-attestation for the unresolved path.** `[bd10:27]`: AC3 asserts there is no
  `model_invocation_attested`, but AC6a/AC7a do not. A GREEN that attests before refusing would pass them.
- **E3 no run context.** Hook raises, hard gate, no `telemetry_ctx` run: it must still refuse and must not raise
  (AC-P8). Not tested.
- **E4 hook raising `BaseException`** (KeyboardInterrupt/SystemExit). "Never raises" is ambiguous. The spec should say
  `except Exception`, so Ctrl-C is not swallowed into a degrade.
- **E5 whitespace or unknown-family effective** (`" "`, `"OPUS "`, an Azure name). For a gate this is refused by the
  floor, which is fine. For a worker it is recorded verbatim, and `bd_l3`/R3.3 then reports "not-checked" silently. Accepted
  behaviour, but undocumented.
- **E6 deployment-name trust.** The hook reports a deployment *label*. An Azure deployment named `fable` that serves
  a small model passes a hard gate (enshrined by ac10d). The trust model is the same as the base (where `deployment == "opus"` passed),
  but the spec should state that the floor checks the declared name and not the served weights.
- **E7 effort keyed on requested vs effective.** This is declared out of scope, but no test pins it, and the tests stub both
  `_load_effort*` functions. A GREEN (or the bd#107 rebase) that keys effort on `effective` would not be caught.
- **E8 fallback with a hooked agent-sdk** (overwrite registration with a hook): the fallback dispatch drops the hook. This is
  consistent with the design, but nothing tests it.

## Findings

1. **MAJOR: `model_requested` semantics change contradicts the normative AUTHORSHIP_SPEC and is not in scope.**
   `conformance/AUTHORSHIP_SPEC.md` AC-M3 (:643-654) defines `model_requested` as "the POST-rebind **dispatched**
   model" and the R3.3 comparison target as "the dispatched request model". After bd#103 the backend is dispatched with
   `model="opus"` while `model_requested == "fable"` (AC4) or `"haiku"` (AC5). So the conformance contract,
   which third-party adapters and `bd_l3` consumers read, becomes false. The `_attest_payload` docstring
   (:1229-1230) says the same thing. Spec §2.3.5 calls the new value "the documented meaning", which is not accurate. Also,
   when a hook remaps, the log no longer records the requested/pinned model at all (nine keys stay fixed),
   and the spec does not acknowledge that loss of evidence. Fix: add `engine_py/bytedigger_engine/conformance/AUTHORSHIP_SPEC.md`
   (AC-M3 amendment: `model_requested` = effective model as declared by the backend's hook, equal to the dispatched model
   when there is no hook) and the `_attest_payload` docstring to §5. State the evidence trade-off explicitly in §2.3.5.
   §1g one canonical source: two normative texts must not disagree on one field.
2. **MINOR: §4 sibling list is incomplete.** The grep for `hard_gate_refused`/`model_requested`/`PYDANTIC_BACKEND_DEPLOYMENT`/
   `E_HARD_GATE_MODEL_DOWNGRADE` also hits `test_llm_subprocess_23680DDA.py`, `test_bd29_in_session_pin_fail_closed.py`,
   `test_bd28_bd_l3_checker.py`, `test_bd73_r31_r32_verdicts.py`, `test_bd63_r35_enforcement_falsifiable.py`,
   `test_bd141_p4_bd_l3_cli.py`, `test_bd155_l2_event_type_key.py`, `test_gh426_fable_model_floor.py`,
   `test_68E964FB_llm_backend_registry.py`, `test_02FF48F4_model_pin_insession.py`, `test_2FDA949D_model_pin_warn.py`,
   plus the pydantic_openai importers `test_GH873_usage_property_gate.py` and `test_gh898_backend_pip_hint.py`. None of them looks
   behaviour-affected (no hook means byte-identical output; in-session is out of scope), but they belong in the must-stay-green list.
3. **MINOR: ac10d is outside the spec.** It is grounded in §1.4/§2.4 and is the only test proving the stricter local check is
   gone in the meets-floor case through the chokepoint. Add it to §3 as AC10(d) so spec and RED agree.
4. **MINOR: no AC for E1 (hook gets the post-rebind model) or E2 (no attestation on an unresolved refusal).** Both are cheap
   assertions that close real wrong-GREEN shapes. Recommend adding them to AC8 and AC6a/7a.
5. **MINOR: §2.2 should say `except Exception`** (E4), and should say whether a hook that returns a whitespace-only str is a
   "problem" (E5).
6. **MINOR: the §2.3.2 refusal message contract** (names the backend, says the effective model cannot be resolved) is not
   asserted anywhere.
7. **MINOR: docs.** `docs/backends.md` (register_backend section, around :122, and the `PYDANTIC_BACKEND_DEPLOYMENT` bullet at :72)
   should document the new public `effective_model=` kwarg and that a hard gate floor-checks the deployment name.
   §5 lists only CHANGELOG.
8. **MINOR: E6/E7 trust and effort notes** belong in §2.4 / §1v as explicit statements, so a later reader does not
   take the floor as a check on the served weights, or take effort as tracking the effective model.

The design itself (single chokepoint resolution, fail-closed gate / degrade worker, the backend still called with the
requested model, the protocol unchanged, the provider-agnostic floor via `get_provider()`) is sound and matches the issue. RED is
adequate and not vacuous. The rejection comes only from finding 1, a contract-scope defect that can be fixed in the spec
(it adds a doc file to §5 and states the semantics). RED does not need to change for it.

VERDICT: REJECTED
