## Adversarial edges (not covered by the §3 ACs)

1. **The git subprocess chokepoint is invisible.** About 80 direct `git_port.git_read(...)` / bare `git_read(...)`
   calls under `workflows/` and `lib/` collapse into one key, `lib/git_port.py::_git_read_subprocess::bounded_run#0`
   (git_port.py:98). A new `git_read([...diff...]).stdout` inlined into a prompt never reddens. Today the diff is
   handed over by path (phase_5_integrity.py:331/371, phase_6_fix_integrity.py:493). See MAJOR-1.
2. **Import alias of a wrapper.** `from ...bounded_spawn import bounded_run as br; br(...)` is not matched, because
   wrappers match by bare or attribute name only. It is not in the declared limits. No such alias exists in the tree
   today.
3. **Comprehension and generator scopes.** "Python `__qualname__` form" is version-dependent. PEP 709 (3.12+) inlines
   list/dict/set comprehensions, but generators still get `<genexpr>`. The spec does not pin either.
4. **Duplicate qualnames in one module.** Examples: conditional `def f` in `try`/`except`, a property getter and
   setter, `@overload`. The spec does not say whether ordinals pool or collide.
5. **Reads in a default argument or decorator expression.** The spec does not assign them to a scope.
6. **The AST rule's trigger key.** The AC15 AST rule fires on `"role_template"`. A forwarding dict that carries
   `"prompt"` for a later re-dispatch but has no `role_template` escapes it, for example `phase_6_review.py:1086`
   `extra`. That dict is not re-dispatched today.
7. **Stale-key problem strings.** There is no site, so no `file:line` and no source line can be printed, which
   contradicts spec:137 "every problem string ... names the key **and** its `file:line`".
8. **Spawn vs read-back class.** T1's spawn (`_verify_green_passing::run_test_command#0`, :5123) writes the stdout
   that the `_read_text_or_empty#0` read inlines. The spec does not say which call carries the class. The rule
   "the call whose return value holds the bytes" is implied but not stated. If GREEN classifies the spawn as
   I-deferred/192, it fails test:905-906.

## Findings

**MAJOR-1: the r1 MAJOR-1 fix is incomplete: `git_port.git_read` is missing from `WRAPPER_CALLEES`.**
(spec:123-128; test:744-764)
- r1 MAJOR-1 rejected because "the lint cannot see the engine's real subprocess chokepoint". r2 added `_git_read`
  (`phase_workflows_common.py:66`), but that is a thin wrapper over `git_port.git_read` (`:78`).
- About 80 workflows/lib sites call `git_port.git_read` directly or as the imported `git_read`. Examples:
  phase_5_integrity.py:292, phase_6_fix_integrity.py:461, phase_45_spec.py:1329/3388, lib/authored_boundary.py:122.
  So do the `git_port` helpers `rev_parse` (git_port.py:190), `status_porcelain`, `ls_files_others` and
  `worktree_list_porcelain`.
- All of these resolve to the single key `lib/git_port.py::_git_read_subprocess::bounded_run#0`, which can carry
  only one class.
- The subprocess-stdout clause of class I (AUTHORSHIP_SPEC §4:472-473) therefore still has no detection for its
  largest family, and spec:10 and :156 ("A new raw read therefore reddens") stay false for it. The generic limit
  "wrappers not in `WRAPPER_CALLEES`" (spec:134) hides a known existing chokepoint; it is not a declared residual.
- **Required fix:**
  - Spec: add `git_read` (bare name and attribute name) to `WRAPPER_CALLEES`. Add the `git_port` read helpers too,
    or state that they are not-prompt by construction and declare them as a named limit.
  - Test: add an AC11 grammar case (`git_port.git_read([...])` and bare `git_read(...)` → `::git_read#n`) plus an
    unkeyed-reddens case.
  - Optionally, consider deriving wrappers transitively (any function whose body returns a keyed spawn's result).
