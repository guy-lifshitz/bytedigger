## Adversarial edges (not covered by §3)

1. **Readiness refusal short-circuits the event.** If `_readiness_review_gate` returns NOT_APPROVED, `_build_review_prompt` returns before the op2 check, so a truthy key emits nothing on that run. Harmless, because the run is refused anyway. Not pinned.
2. **Re-entry: "once per run".** §2 and §6 say `_build_review_prompt` runs once per run. If a fix cycle replays phase 6 from step 0 (or the orchestrator re-attempts with `last_findings.json`, :735), the event repeats per attempt. No prod consumer counts it (grep). This is the same exposure `review_fanout_ignored` already has (A1).
3. **Truthy strings that read as false.** `"false"`, `"0"` and `"no"` are truthy under `bool()`, so they emit with that value. This is deliberate (same truthiness as the removed reader), but AC4 pins only `"yes"`. Acceptable, because the event is advisory only.
4. **Environment leak into AC5.** `get_role_model` also consults env `HAL_MODEL_UNAVAILABLE`. A dev shell with `opus` or `sonnet` marked unavailable would still return the chain head (degrade path :133-134), so AC5 stays green. No flake, but the test does not isolate the env (A2).
5. **Resume across the upgrade.** A pre-upgrade scratchpad can hold an `invoke_decorr_llm` resume sentinel. After the removal no step reads it (orphan, harmless). Any persisted integer `start_step` ≥ 14 from a pre-upgrade phase-6 run would land on a different step. `_fix_step_index` resolves by name, so only an externally stored integer would be exposed. Not pinned (A3).
