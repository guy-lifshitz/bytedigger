# bd#73 — R3.1 and R3.2 get a verdict

**Class:** declared ≠ checked. The label exists, the evidence exists, and there is no
adjudication. The same form as bd#59 (the observation registry), bd#68 (no producers), bd#71
(the evidence discarded along the way) — its fourth variety.

**Chokepoint:** `conformance/bd_l3.REQUIREMENTS` and `_CHECKS` — the only place where a
requirement gets a verdict.

## §3. THE HONEST BOUNDARY OF R3.2 — named, not glossed over

The bd#10 chokepoint validates injections **before** the dispatch and on refusal **emits nothing**
(`[bd10:27]`: "an attestation exists if and only if a dispatch occurred").
⇒ An unattributed injection never reaches the log **by construction**, and the R3.2 verdict on
a real log is a **confirmation**, not an independent check.

It has value all the same, and that value is named precisely: a **chokepoint regression
guard**. If the validation stops refusing, a block will reach the attestation and R3.2
will fail. Passing this off as an independent check is not permitted — that would produce exactly the
green shield we have been dissecting all the way through.

**R3.1 needs no such caveat:** the prompt hash is always written, and its absence or
wrong form is an observable violation in its own right.

## §4. Decisions

**D1 — R3.1 is violated** when `prompt_sha256` is absent, is not a string, or is not in the form
`sha256:<64 hex>`. The form is pinned, not just presence: a key with the value `"ok"` would
satisfy a presence check and would not be a hash.

**D2 — R3.2 is violated** when at least one `injections` block lacks `source_id` **or**
`sha256`. **Both halves of the conjunction**, not one: checking only `source_id` would leave
the second unreachable.

**D3 — an empty injections list is legitimate.** An invocation with no injections does not violate
R3.2; there is no observation of it ⇒ `not-checked`. Treating the absence of injections as a violation
would mean requiring injections of every step.

**D4 — a gate against recurrence:** every label in `REQUIREMENT_LABELS` must have a
verdict or stand in a declared exception list. The absence of such a gate is what produced
this gap; it is placed over **all** labels, not over the two that were fixed.

**D5 — no new code is introduced.** `E_INJECT_UNATTRIBUTED` is already registered and already
emitted by the chokepoint; R3.2 names that same one. Breeding a second code for the same condition is
a duplicate guard (the bd#65 lesson).

## §7. Acceptance criteria

- **AC1 (R3.1, positive).** A correct `sha256:<64 hex>` ⇒ `passed`.
- **AC2 (R3.1, NEGATIVE).** Absent ⇒ `failed`.
- **AC3 (R3.1, NEGATIVE — the form, not presence).** `"ok"` instead of a hash ⇒
  `failed`. Catches a "the key is there" check.
- **AC4 (R3.2, NEGATIVE, both halves).** A block without `source_id` ⇒ `failed`
  with `E_INJECT_UNATTRIBUTED`; a block without `sha256` ⇒ the same. Two inputs, because it is
  a conjunction.
- **AC5 (R3.2, positive).** A complete block ⇒ `passed`.
- **AC6 (D3).** An empty injections list ⇒ **not** `failed`.
- **AC7 (THE GATE, D4, both sides).** Every `REQUIREMENT_LABELS` label has a verdict
  or is declared an exception; an exception that has acquired a verdict fails the gate.
- **AC8 (the R3.2 boundary is declared).** The predicate's docstring states that on a real log
  this is a confirmation and a regression guard, not an independent check.
- **AC9 (surface = `__all__`, `REQUIREMENTS` grew deliberately).**

## §8. What the PR does NOT claim

- **It does not claim that R3.2 is checked independently** (§3) — on a real log it is
  a confirmation and a chokepoint regression guard.
- It introduces no new codes (D5) and no new producers.
- It does not touch R3.4 or the bd#10 decision about it.
