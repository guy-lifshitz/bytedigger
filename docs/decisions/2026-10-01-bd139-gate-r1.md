> engine_py/tests/test_bd82_role_backend_effort.py:207:     assert seen and seen[0].get("straggler_cfg") is not None

`test_r8b_global_in_session_does_not_drop_a_subprocess_judges_straggler` sets `straggler_abort=True`

### BLOCKER — single-mode prompt still addresses sub-agents on the re-review and security paths
> engine_py/bytedigger_engine/workflows/phase_6_review.py:858:             f"Each dispatched Agent MUST read the prior findings file before reviewing:\n"
> engine_py/bytedigger_engine/workflows/phase_6_review.py:913:             "\nSECURITY ADDENDUM (security_classification=HIGH): after all sub-agent "

The fix loop writes `reviews/last_findings.json` (`:3592`), so every re-review cycle in single mode
gets a directive aimed at agents that no longer exist. The single reviewer may then skip the
prior-findings read, which breaks the "PRIOR — still present" convergence. AC3 checks only the
first-attempt prompt and only the literals `Spawn` / `parallel` / `Agent tool`. Both blocks pass
AC3 unchanged, and the 7CA211D2 sibling was pinned to parallel, so nothing guards single mode.
**Required:**
- §2 op1 states the single-mode wording of the 7CA211D2 propagation block and the SECURITY
  ADDENDUM: addressed to the reviewer itself, with no sub-agent or Agent-call language. Add
  `phase_6_review.py:849-918` to the op1 description.
- New AC3b: single mode with `last_findings.json` present and `security_classification="HIGH"`.
  The prompt contains the absolute `last_findings.json` path and `PRIOR — still present`, and
  contains none of `dispatched Agent`, `sub-agent`, `Agent call`, `Spawn`.

### BLOCKER — composite checklist and devops focus are stub-passable
> engine_py/tests/test_bd139_single_reviewer.py:98:     assert "devops" in table

that drops the dispatch table entirely. §2 says the composite row "covers the dimensions of the six

### BLOCKER — op2 logs only the terminal round, but the stated metric is per round
> docs/decisions/2026-10-01-bd139-phase6-single-reviewer.md:61: - `_gate_on_validation` calls it before returning the terminal error. A logging failure is
> engine_py/bytedigger_engine/workflows/phase_5_implement.py:6943:         if cycle < cap:
> docs/decisions/2026-10-01-bd139-phase6-single-reviewer.md:122: - **Gate rounds rejected for script-catchable reasons:** baseline from the lot's classifier

Rejected rounds below the cap return `status="ok"` at `:6943-6971` and, per the spec, write no row.
Only the final round of a run that fails out is logged, so `detail.cycle` always equals the cap.
The §5 per-round classifier then sees runs, not rounds, and loses every round that was rejected and
later fixed. Those rounds are the main signal for "script-catchable" rejects.
**Required:** decide and state one of:
- (a) Log every FAIL/UNKNOWN round, including `cycle < cap`. Add an AC: a FAIL at `cycle=1 < cap`
  appends one row with `detail.cycle == 1` and still returns status ok with `cycle == 2`.
- (b) Terminal-only, with §1.3 and §5 rewritten to a per-run metric, plus an AC asserting no row at
  `cycle < cap`.

Either way, state whether the spec-defect exits (`:6872`, `:6904`, `:6927`) log a row.
