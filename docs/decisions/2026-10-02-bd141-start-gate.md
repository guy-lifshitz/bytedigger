## §1 Problem (measured on `97b84e8`)

1. bd#141 item 6: "Implementation does not start without `plan-approved`." bd#117 shipped this
   for **engine-driven** builds only at ship time: `phase_8_post_deploy._ship_to_pr`
   (`workflows/phase_8_post_deploy.py:570-592`) calls `readiness.verdict(cwd, "ship")`.
2. Engine Phase 5 (`phase_5_implement_workflow`, `phase_5_implement.py:8461`) runs RED
   (`invoke_red_llm`, writes the test file into the repo) and GREEN (`invoke_green_llm`, writes
   code, `commit_green_code`) with no readiness check. Grep on `97b84e8`:
   `grep -n readiness engine_py/bytedigger_engine/workflows/phase_5_implement.py` → 0 hits.
3. Under `readiness.required: true` an unapproved engine build therefore spends the whole RED →
   gate → GREEN cycle (Opus validation + GREEN calls) and is refused only at Phase 8. bd#117
   names this failure mode "wasted local work" and defers the fix to v2. `readiness.verdict`
   already supports `stage="start"` (spec-binding `spec_changed`, never consumes); only the
   engine caller is missing.

## §2 Design

### op1 — `_readiness_start_gate(ctx, prev) -> StepResult | None` (new helper, `phase_5_implement.py`)

- Module-level import `from bytedigger_engine import readiness as _readiness` (same alias as
  phase 8; tests monkeypatch `p5._readiness.verdict`).
- `repo, source = _resolve_git_cwd_with_source(ctx, prev)` (GH1220 §1g).
- **Ambient guard (r2, gate r1 MAJOR-1):** if `lib.git_cwd.is_ambient_git_cwd(source)` the
  readiness call is **skipped** — `readiness.verdict` mutates the repo (`git fetch` into
  `refs/bd/policy`), and an ambient cwd is never mutated (GH1220). The helper emits the event with
  `verdict="UNAVAILABLE"`, `reason="ambient_git_cwd"`, other values `None`, and returns `None`
  (fail-open, as below).
- `spec = _resolve_scratchpad(ctx) / SPEC_DOC_RELPATH`; `spec_path = str(spec) if spec.is_file()
  else None` (absent spec ⇒ the record/label checks still run; `spec_changed` is skipped, as in
  `readiness._evaluate`). An exception while resolving the spec degrades to `spec_path=None`
  (r2, MINOR-3) — evaluation continues.
- `gate = _readiness.verdict(repo, "start", spec_path)`. Any exception from the call or from
  resolving the repo ⇒ treated as `{"verdict": "UNAVAILABLE", "reason": "internal error: <repr,
  one line>", "issue": None, "record_sha256": None}`.
- Mapping:
  | verdict | helper returns | event |
  |---|---|---|
  | `OFF` | `None` (proceed) | none |
  | `APPROVED` | `None` | `readiness_start_verdict` |
  | `UNAVAILABLE` | `None` (fail-open, warn) | `readiness_start_verdict` |
  | `NOT_APPROVED` | error `StepResult` (below) | `readiness_start_verdict` |
- Error `StepResult`: `status="error"`, `data=None`, `duration_ms=0`,
  `step_name="validation_cycle_loop"`, `error=f"readiness: not approved ({reason}) #{issue_tag}"`
  where `issue_tag = "" if issue is None else str(issue)` (byte-identical to phase 8's format),
  `error_code="E_READINESS_NOT_APPROVED"`, `recoverable=False`.
- Event: `_emit_safe("readiness_start_verdict", {"stage": "start", "verdict": ..., "reason": ...,
  "issue": ..., "record_sha256": ...})` — exactly these five keys, values copied from `gate`.
- Never posts a record, never consumes, never edits labels (it only calls `verdict` at `start`).

**Why fail-open on UNAVAILABLE:** matches the op-A3 prompt contract ("anything else warns and
continues" at start) and bd#117's layering — the start gate saves wasted work, the ship gate
(fail-closed) is the enforcement layer. An outage must not block local work.

### op2 — call site: top of `_validation_cycle_loop_execute`

First statement of the composite: `refusal = _readiness_start_gate(ctx, prev); if refusal is not
None: return refusal`. Runs before the GH767 reroute sentinel logic (`phase_5_implement.py:7892-7911`;
a refused run must not consume the reroute marker or invalidate cycle-1 sentinels) and before
`LoopRunner`, so before `invoke_red_llm` / any repo write. The workflow's `steps` list is
**unchanged** (no new `StepContract`), so callers that index or name steps are unaffected.
Re-entry (later cycle, reroute, resume) re-runs the gate; `start` never consumes, so it is
idempotent. A rerouted (revised) spec under a required policy yields `spec_changed` ⇒ refusal:
approval binds the posted spec (bd#117), so a revised spec needs a new `readiness post` + label.

## §4 Declared limits

- Advisory against the model, like bd#117 (the orchestrator has Bash/gh). The engine gate makes
  an unapproved engine build stop before RED instead of at Phase 8; it does not stop a direct
  `git push`.
- Every Phase 5 entry (including resumes) with **any** `origin` and a non-ambient git_cwd now does
  the policy read (`ls-remote` + one fetch of the default branch into `refs/bd/policy`), even when
  the policy has no `readiness` key — as Phase 8 already does when it ships. No origin ⇒ no
  network. No latency AC (no numeric claim is made).
- Concurrency: parallel Phase 5 entries in worktrees sharing one object store race on
  `refs/bd/policy`; the loser gets UNAVAILABLE and its start gate is skipped (fail-open, event
  recorded). The ship gate still fails closed.
- No `awaiting_approval` state machine in the engine: a refusal is a non-recoverable phase
  failure; resume after the human adds the label.
- Review-readiness gate ("review does not start without the ready label") and item 5's revert
  signals stay out (bd#117 §1v list); next lots.
