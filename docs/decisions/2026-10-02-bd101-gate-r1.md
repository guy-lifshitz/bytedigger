## Adversarial edges (not already covered by the §3 AC table)

1. **Direct `agent_sdk_backend` callers that expect warm behaviour.** No AC covers what the Change 4 flip does to callers that bypass the dispatcher. Four sibling tests do exactly that (finding 1).
2. **`hard_gate=True` with an explicit `role="worker"` on a listed step.** This is the only input where the `or hard_gate` chokepoint term is load-bearing. Every gate test in both bd#82 and bd#101 omits `role`, so `effective_role` silently becomes `judge` (finding 3).
3. **Same-key isolation on a listed writer.** The planned f4b amendment moves the fresh calls to a different key, so "a fresh call does not touch the warm session" stops being tested (finding 2).
4. **Lint blind spots.** `executor.submit(..., invoke_llm_subprocess, step_name=..., hard_gate=True)` and `invoke_llm_subprocess(**invoke_kwargs)` built from `dict(...)` are invisible to the AC10 scan (finding 4).
5. **An unlisted writer silently going fresh.** `invoke_synthesizer_llm` is a writer that the spec neither lists nor declares as deliberately fresh (finding 5).

## Findings

### 1. MAJOR: Change 4 breaks four undeclared sibling tests, and the spec's amendment rule cannot repair them

The flip of `agent_sdk_backend(fresh_session=...)` to default `True` affects every caller that invokes the backend directly without the keyword. At agent_sdk.py:396 such a call now gets `key=None` and never reads or writes `_SESSION_CACHE`. These existing tests do exactly that and assert warm behaviour:

- `engine_py/tests/test_GH901_agent_sdk_cost_rollup.py:388-393`: two direct calls, then `assert r2.data.get("warm_resumed") is True`. This will fail.
- `engine_py/tests/test_gh956_agent_sdk_success_salvage.py:316-330` (`test_ac7_salvage_path_still_caches_session`): `assert mod._SESSION_CACHE.get("r1:phase_5") == ("sess-salvage-1", 0)`. This will fail because the cache is never written.
- `engine_py/tests/test_gh956_agent_sdk_success_salvage.py:407-424` (`test_ac10_...no_cache_invalidation`): the same cache assertion at :421. This will fail.
- `engine_py/tests/test_gh1157_agent_sdk_retry.py:327-358` (`test_ac6_retry_then_success_resets_resume`): the cache re-population assertion at :356 will fail. The "poisoned resume" assertion at :352 still passes, but vacuously: resume is now None because the call is fresh, not because of the retry reset.

(`_common_kwargs` in each file, e.g. test_gh1157_agent_sdk_retry.py:169-179 and test_GH901:126-132, passes no `fresh_session`.)

The spec's catch-all (spec lines 81-83) says to amend such a test "to a listed writer step". That does not work here: the backend never consults `_WARM_RESUME_STEPS`, so renaming `gate.step1` or `phase_5.x` changes nothing. The same paragraph then classifies the failures as regressions ("A test that fails for any other reason is a regression"). GREEN would be forced to either violate the spec or edit undeclared tests.

**Fix (spec r2):** add these four tests to "Sibling amendments (declared)". The amendment is to pass `fresh_session=False` explicitly in the direct `agent_sdk_backend(...)` calls (keep the step names), which preserves what each test means: warm-path cache write, salvage cache write, and retry resets a *warm* resume. Extend the catch-all: "a test that calls `agent_sdk_backend` directly and expects warm behaviour passes `fresh_session=False`." Optionally add a guard AC that a direct call with `fresh_session=False` still writes the cache, so the warm path inside the backend stays shielded at the unit level.

### 2. MINOR: the declared f4b amendment turns a same-key shield into a different-key tautology

Spec lines 72-77 move the warm calls of `test_f4b_fresh_call_leaves_the_warm_session_alone` (test_bd82_fresh_sessions_thread_ctx.py:149-164) to `invoke_fix_llm` and leave the fresh calls on `invoke_review_llm`. Two different keys cannot collide, so the test no longer proves that a fresh call leaves the warm entry alone. The spec itself admits "Different key now".

**Fix:** put all four calls on `invoke_fix_llm`: warm, then `fresh_session=True`, then failing `fresh_session=True` (prompt `"fail"`), then warm. The expected result stays `[None, None, None, "sess-1"]` and the cache equality at :162 still holds. This keeps the same-key proof that bd#82 intended.

### 3. MINOR: the `hard_gate` precedence term is never discriminated

Under the spec's precedence (spec lines 60-64), "not a hard gate" is the first condition. But `effective_role = role or ("judge" if hard_gate else "worker")` (llm_subprocess.py:1912) means every gate test that omits `role` is fresh via the judge rule alone. That covers AC5, AC7, bd82 f6b :204-218 and f6d :244-259. A GREEN that drops `or hard_gate` from the chokepoint (keeping only `or judge or not allowed`) passes everything. A `role="worker"` hard gate on a listed step would then hand `fresh_session=False` to any third-party `warm_resume` backend. agent-sdk is still protected by its own rule at agent_sdk.py:396.

**Fix:** add an AC7 case: warm spy, `step_name="invoke_green_llm"`, `hard_gate=True`, `role="worker"`, expect `fresh_session is True` on both `stable_prefix` branches.

### 4. MINOR: the AC10 lint has two blind spots the spec does not list

`_llm_calls` (test_bd101_fresh_default.py:282-291) yields only `Call` nodes whose callee is `invoke_llm_subprocess`. It does not see:

- phase_6_review.py:2994-3008: `executor.submit(run_with_current_run, parent_ctx, invoke_llm_subprocess, step_name="invoke_satisfaction_llm", hard_gate=True, ...)`.
- phase_45_spec.py:3955-3971 and :3919: `invoke_kwargs = dict(step_name="invoke_review_llm", hard_gate=True, ...)`, then `invoke_llm_subprocess(**invoke_kwargs)`.

So "no gate uses a listed step name" silently skips 2 of the 6 hard-gate families. There is no false negative today, because neither family is listed, but a future rename onto a listed name would pass.

**Fix:** either extend the scan to (a) `Call` nodes with a positional `Name("invoke_llm_subprocess")` argument and (b) `dict(...)` calls with both `step_name` and `hard_gate` keywords, or add both forms to "Known limits" next to the dynamic-step_name limit.

### 5. ADVISORY: one unlisted writer goes fresh and the spec does not declare it

`invoke_synthesizer_llm` (phase_7_synthesize.py:584-599, tools Read/Write/Glob) is a writer that loses warm resume. This is consistent with the issue's writer list (implement, fix, directed repair) and costs money, not correctness. Because the spec does not mention it, a reviewer could read it as an oversight.

**Fix:** one line under "Known limits" or "Change 1": "`invoke_synthesizer_llm` is deliberately not listed (single call per run; fresh)."

### 6. ADVISORY: Change 6 (docs / CHANGELOG) has no AC

**Fix:** either accept it as review-only and say so in the spec, or add a cheap assertion: the first `## [Unreleased]` → `### Changed` section (CHANGELOG.md:101) contains `_WARM_RESUME_STEPS`, and there is no second `### Changed` under Unreleased (the bd119 F8 constraint).

### 7. ADVISORY: AC8 relies on the ambient environment

`_fallback_hang_attempts` returns None when `HAL_AGENT_SDK_HANG_FALLBACK=0` (llm_subprocess.py:1757). bd82 f6d has the same exposure. **Fix:** `monkeypatch.delenv("HAL_AGENT_SDK_HANG_FALLBACK", raising=False)` in the AC8 test.

### 8. ADVISORY: third-party backends and step-name coupling

- A third-party backend that resumes internally without declaring `warm_resume` is outside the engine's reach. The new `register_backend` docstring should say: "a backend that keeps sessions must declare `warm_resume`; undeclared backends should treat every call as fresh."
- The dispatcher now holds workflow step names, which is an inverse dependency. That is acceptable under the workflows/ and phases/ freeze. Recommend a follow-up note to move the table to the #100 per-role policy once call sites can change.
