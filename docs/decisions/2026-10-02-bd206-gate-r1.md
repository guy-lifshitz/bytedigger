## Findings

### MAJOR

**M-1. The checker is not run-scoped, which contradicts AUTHORSHIP_SPEC §4.**
- §4 (`AUTHORSHIP_SPEC.md:514-517`): a class-M `source_id` names "an earlier attestation **in the same run**". Spec §2.6 keeps one `(step_name, invocation_id)` set across the whole iteration.
- `check_bd_l3` filters by run only in the CLI, when `--run-id` is given (`bd_l3.py:384-386`). The in-process API and the CLI without `--run-id` would accept a block in run B that names an attestation from run A.
- That is the same cross-run case the producer refuses in §2.4, so the oracle is weaker than the producer it judges.
- **Fix:** key the seen-set by `(event["run_id"], step_name, invocation_id)` and look up with the current event's `run_id`. Add an AC7 case where run B names run A's attestation, the two runs interleaved in one log, and expect R3.2 `failed`.

**M-2. AC7 cannot express "both directions" as written, and it misses the add-before-check boundary.**
- "On one synthetic log: … later → `failed`; the same block after it → `passed`." A report carries one R3.2 verdict per log (`bd_l3.py:281-292`), so one log cannot assert both. A RED that puts every case in one log and asserts `failed` is satisfied by a checker that fails every `invocation:` block.
- The spec never tests self-reference, i.e. a block naming its own payload's `invocation_id`. A GREEN that records the current pair before checking that payload's blocks accepts self-reference and passes AC1-AC8.
- §2.6 exempts `output_sha256: null` ("present and not `None`"), but no AC holds that. A GREEN that flags `null` passes AC7's real-log case, because AC1's backend always returns a str, and it would then fail R3.2 on production logs with `data=None` results (`llm_subprocess.py:1311-1314`).
- **Fix:**
  - Give each AC7 case its own log, and assert the `passed` case as R3.2 `passed` with `violations == ()`.
  - Add a self-reference case (expected `failed`).
  - Add `{"invocation_id": <valid>, "output_sha256": null}` (expected no violation).
  - State in §2.6: "check the payload's blocks against the pairs from strictly earlier events, then add this payload's pair".

**M-3. The `run_id` source is unpinned at all four sites.**
- §2.3 (writer), §2.4 (sidecar write and review-prompt read) and §2.5 (verifier) compare `run_id`s but never say where the value comes from.
- Phase 6 resolves it as `telemetry_ctx.get_current_run().run_id` (`phase_6_review.py:4080`). The semantic verifier's own events use `ctx.session_id` (`semantic_verifier.py:383`, `:576`). A GREEN that follows the verifier's local convention at one site would make `review_source_id` return `None` silently at that site.
- AC6 catches that only if RED's fixture happens to make `ctx.session_id` differ from the telemetry run id. The chokepoint claim ("ONE writer/reader pair") is incomplete without the key it compares.
- **Fix:** add to §2.3: "`run_id` is `telemetry_ctx.get_current_run().run_id` at every site. With no current run, nothing is written, the sidecar `run_id` is `null`, and nothing is declared." In AC4 and AC6, set `ctx.session_id` to a value different from the telemetry run id, so that a `session_id` GREEN fails.

### MINOR

**m-1. The `n_valid==1` survivor in §2.2 can never be reached.** `phase_6_review.py:3934-3944` returns `E_REVIEW_DEGRADED` for `n_valid < 2` before the FAIL block, and `:4013` repeats the guard. **Fix:** delete the survivor clause from §2.2, or mark it unreachable and say GREEN must not add code for it.

**m-2. §2.3 has a factual error and contradicts itself.**
- "As it unlinks `doc_path`" is false: `_invoke_review_llm` (`:1053-1061`) only removes `role-*.md`.
- "A failed … review leaves none" conflicts with "writes when the result carries a valid `invocation_id`": error results and the pin/escape refusals carry the id (`llm_subprocess.py:1762-1770`, `:1371`, `:1410`).
- **Fix:** "write only when `result.status == "ok"` and `data["invocation_id"]` is 32-hex". Add an AC4 case for an error result **with** an id: expect the file to be absent.

**m-3. AC8's R3.2-row clause is vacuous on base.** `AUTHORSHIP_SPEC.md:376` already contains `bd#206`, and `test_bd152_output_digest.py:489` already asserts it. **Fix:** assert that the row no longer contains "class-M block declarations are a follow-up (bd#206)" and that it does contain a "declared … (bd#206)" phrase. AC8 should also require that the class-M paragraph keeps the literal `invocation:<step_name>:<invocation_id>`, which bd152's AC10 (`:484`) pins and which §2.7's rewrite could drop.

**m-4. M2 declares a block with no model text when the findings are empty.** `_prior_structured` defaults to `[]` (`:938`), which renders as `"[]"`. That string is non-empty, so §2.1's rule lets a block attributed to the review invocation through with zero model bytes. **Fix:** declare only when `structured_findings` is a non-empty list, and add the case to AC5.

**m-5. The normative text has no class-M chunk rule, and the three sites use three granularities.**
- M1's content includes the engine's `"- "` and `": "` markers (`:3573`).
- M2's content is the whole `json.dumps` output, JSON syntax included.
- M3's content is the bare field values, without the `File:`/`Quote:` labels (`semantic_verifier.py:149-152`).
- The Chunk rule (`AUTHORSHIP_SPEC.md:521-526`) is written for class I ("class-E wrapper and markers in no block"). Read as applying to class M, M1 and M2 break it.
- M3's content must also be `str(value)` as rendered: a caller can pass `"line": 1` (`test_bd82_role_backend_effort.py:160`), and a non-str `content` is refused (`llm_subprocess.py:1078`).
- **Fix:** have §2.7 add a class-M chunk sentence to AUTHORSHIP_SPEC (one block per carried unit, content = the string as inlined, with M1 markers inside the block declared as a limit). State in §2.5 that the content is `str(finding[k])`.

**m-6. No AC covers `invoke_fix_llm_retry`.** The FIX_NO_MARKER retry (`:2603-2637`) declares through the same bound record. **Fix:** extend AC1 with a first fix response that has no marker, and assert that the `invoke_fix_llm_retry` attestation carries the same class-M block.

**m-7. The §4 sibling list is incomplete.**

## Adversarial edges (not covered by the §3 AC table)

1. **Cross-run reference in one log.** Run B's block names run A's attestation, and the runs are interleaved. Expected R3.2 `failed` (M-1).
2. **Self-reference (off by one).** A block names its own payload's `invocation_id`. Expected `failed` (M-2).
3. **`output_sha256: null` with a valid `invocation_id`.** Expected no violation. This guards real logs with `data=None` results (M-2).
4. **Failed but attested review.** `_invoke_review_llm` gets status `error` with a stamped id (for example `E_MODEL_PIN_MISMATCH`). Expected: no provenance file (m-2).
5. **Empty prior findings.** A sidecar with `structured_findings: []` from the same run. Expected: no class-M block (m-4).
6. **Decoy fence on `sat_loop`.** A review-driven fix prompt (`fix_loop_source` absent) whose `prev.data` carries `findings_blocks` and a matching `findings` string. Expected: no block, and the dispatch is **not** refused with `E_INJECT_UNATTRIBUTED`. A GREEN that skips the `sat_loop` check would declare content that is not in the prompt.
7. **`session_id` ≠ telemetry run_id.** Provenance is written under the telemetry run id. A verifier keyed on `ctx.session_id` must still declare (M-3).
8. **FIX_NO_MARKER retry.** The `invoke_fix_llm_retry` attestation carries the same class-M blocks as the first fix attestation (m-6).
